## 3. Invariants (each one is an incident that already happened)

1. **Never split pasted input on commas or semicolons unless what follows is clearly a new entry.**
   Commons file names contain commas: `File:MKr377445 Susanne Wuest (In die Sonne schauen, Cannes
   2025).jpg` is a real file (pageid 165943740). The Action API does *not* treat a comma as a title
   separator — `titles=File:A.jpg,File:B.jpg` returns one bogus page with HTTP 200 and no warning —
   so both the parser and any batch query must use newlines / `|`. Rules and the reusable
   `to_title()` are upstreamed: Wikipedia-AI-Skills `commons-file-resolution` SOP 6 (PR #93).
2. **A row must never claim to be downloading bytes it already holds.** The prefetch thread once set
   `status="downloading"` before the fetch and left it there while blocked on a full queue, so rows
   read "fetching thumbnail…" for a minute *while displaying the thumbnail*. States are now
   `queued → downloading → ready → scoring → done`, and `downloading` lasts only as long as the
   request. `test_pipeline.py` fails if an item ends in `downloading`/`ready`.
3. **Never rebuild the results list with `innerHTML` on a poll.** It destroyed and re-created every
   row, so every `<img>` was re-fetched — the whole list flashed once a second. Rows are created once
   into a keyed `Map` (see `static/index.html`) and patched in place. `test_ui_contract.py` asserts
   `$("items").innerHTML` does not appear in the JS. **That includes the new-run reset:**
   `clearResults()` removes rows with `removeChild`, never by `innerHTML`, so clearing the list cannot
   re-introduce the reload. **And the row key is identity (`pageid`, else title/raw), never the display
   index** — the list is re-sorted on every poll as ranks move, so an index in the key made every
   re-rank recreate rows and re-assign `<img src>` (found 2026-10-14 while adding the row-order toggle;
   `test_render_dom.js` now proves one `src` assignment survives an order switch).
4. **Cache keys are `(wiki, pageid, sha1, schema_hash, served_width)`.** Pageids collide across
   wikis; titles are renamed; SHA-1 catches file overwrites; the schema hash invalidates answers when
   the questions change. The width is the **served** one (read from the thumburl), not the requested
   one: Commons quantises `iiurlwidth` upward to a ladder step, so a 640 request and a 960 request
   fetch the *same bytes* and must share one entry (§12). `served_w` is `None` for an original
   smaller than the request, in which case the key falls back to `THUMB_WIDTH`. Do not "simplify"
   this.
5. **The About panel and the prompt are built from the same constants.** `about_payload()` in
   `core.py` interpolates `wiclient.STATE` / `wiclient.QUESTIONS`; `test_ui_contract.py` diffs the
   served payload against them field by field. If you edit the schema, the panel follows
   automatically — do not hand-write prompt text anywhere.
6. **All Wikimedia calls stay server-side.** The browser only calls this app. The one exception is
   the browser hotlinking result thumbnails (a deliberate bandwidth choice). If you add a proxy, mind
   the traffic.
7. **429 means stop, not retry harder.** One retry after the server's own `retry-after`, then report.
   No retry loops. `INFLIGHT` workers are allowed within a run (default **1** = serial; v0.5.0
   shipped 2, reverted in v0.5.1 pending the measurement in §7.1) — but every call start
   is reserved through `_next_slot()`, so starts stay SPACING apart *globally*: from the endpoint's
   point of view the app still looks like one well-paced client, and the budget caps the hour.
8. **Input is hostile until proven Wikimedia.** Every URL goes through `wiclient._clean_host()`
   (strict fullmatch on a Wikimedia project domain; userinfo/ports/IP literals rejected) and any
   explicit non-http(s) scheme is refused. Fetches only ever target thumbnail URLs returned by a
   Wikimedia Action API — never a URL parsed out of user input — and are byte-capped
   (`MAX_THUMB_BYTES`, streamed) and pixel-capped (`MAX_SEND_PIXELS`). Runs are item-capped
   (`MAX_INPUT_ITEMS`), the job store is bounded (`MAX_JOBS_KEPT`), and /api/parse is capped
   (`PARSE_MAX`). Do not "simplify" any of these: each one closes a named hole
   (SSRF-via-userinfo, oversized media, unbounded memory/queue).
9. **The composite is our arithmetic, not the model's.** `min(face_visible, eyes_to_camera) × pose
   weight` is computed in `wiclient.composite()` and must be labelled as ours everywhere it appears —
   the UI row, the About panel, the report method block, the README. Never present it as a model
   probability: that would make the number unattributable, which is the one thing this app is built
   not to do. `P(publish)` and `P(infobox)` are the model's own and are always shown beside it.
10. **Report candidate spread, never standard deviation.** sd rises whenever answers pile up at either
   end, *including at the ceiling*, so it rewards exactly the failure we already measured (rewrites
   that pushed every portrait to 0.81-0.96 and shrank the range between them from 0.486 to 0.021).
   `candidate_spread()` reports candidates above a floor, their range, the median gap between
   neighbours, and the dead-zone share — see §11 and `research/wording-experiment-2026-10-13.md`.
11. **Reports must not depend on the network.** Thumbnails are saved to `cache/thumbs/` at fetch time
    and the PDF embeds those bytes, so a report reads the same offline. If you add a new report
    format, embed from `thumb_bytes(item)` (saved copy first, Commons as fallback) rather than
    hotlinking. Also: draw the hairline frame around every embedded image — a white-on-transparent
    logo is otherwise invisible on white paper and the reader cannot tell an image was embedded.
12. **The image box must never arrive pre-filled.** It starts empty, with the accepted formats shown
    only as a grey `placeholder`, and the real starter list arrives on demand from the **Load test
    data** button. A placeholder is not a value: that is what stops anyone pressing *Score them* on
    example text and spending real calls on `Foo.jpg`. Clicking into the box blanks the hint
    (`#input.hint-off::placeholder`), so the user always faces an empty box. `test_render_dom.js`
    asserts the box is empty at load and that the button fills it — this one is a requirement rather
    than a past incident, and it lives here because a pre-filled box is exactly how it would bite us
    next time.
    **One explicit exception:** a URL carrying `?list=` may prefill (see §1 and the memo below). That
    does not violate the purpose — nothing appears unbidden, and a link may press *Validate files* but
    **must never start a *spending* run**. `&run=1` is allowed only as a **cache-only replay**
    (`cached_only`), which resolves the list and serves saved answers while making zero model calls —
    that is what makes a shareable link safe to open, and `test_pipeline.py` asserts the zero both warm
    and cold. Scoring, one call per photo, still takes a click. The URL
    layer must also not grow a second splitter: `?list=` is newline-separated only, because a comma
    occurs in real file names and `|` occurs in the wikitext form the app advertises.
    `test_ui_contract.py` asserts `split(",")` appears nowhere in the page script and that the
    deep-link code calls `$("check").click()` and never `$("run").click()`.

## 4. Traps, measured

**A run that hangs at "n-1 of n" is usually a dead worker thread, not a slow endpoint.** The
pipeline consumer blocks on `q.get()` if the download producer thread dies, so a single traceback in
`_download` looks exactly like the model service stalling forever. Check the server log for
`Exception in thread` before blaming latency. (Real case, 2026-10-13: a `NameError` for a missing
`import re` killed the producer; the run sat at 1/3 for 25 minutes and was misread as the endpoint
degrading to >25 min/call.)

**Never wrap worker code in a bare `except Exception`.** The same NameError was swallowed by the
thumbnail-saving helper, which degraded silently to "no thumbnail in the report" and let the offline
test suite pass. Worker-level handlers catch `OSError` and let coding errors raise — and
`test_pipeline.py` now asserts that every scored photo has a saved thumbnail, so a silent regression
fails the suite instead of shipping.

- **Do not judge a question by its overall spread.** sd rises whenever answers move toward 0 or 1,
  including when they all pile up at the *ceiling*. On the same four photos, a reworded question took
  sd from 0.24 to 0.34 while collapsing the three real portraits into a 0.021 range. Track the range
  and order **among plausible candidates** instead — see §11.
- **The `score` type is not a fix for clustering.** Across 57 cached photos the 0–4 `quality` score is
  the *most* compressed thing we ask (sd 0.145, 60% of photos in 0.35–0.65); a 0–4 variant of the
  infobox question behaved the same way. What spreads is whether the criterion is *visible in the
  frame*, not whether the answer is ordered.
- **A "better-looking" question can rank worse.** Every reworded variant emptied the 0.35–0.65 band
  and every one of them separated the real portraits *worse* than the wording users complained about.
  Always check the candidate range before proposing a wording change.
- **The served thumbnail width is not the requested one — and `imageinfo.thumbwidth` lies too.**
  Commons enforces `$wgThumbnailSteps = [20, 40, 60, 120, 250, 330, 500, 960, 1280, 1920, 3840]` and
  **quantises the request upward** to the next step. Measured on a 4024×6048 original
  (`probe_thumb_ladder.py`): 120→120, 250→250, 320→330, 500→500, **600 / 640 / 800 / 960 → all the
  same `960px-` asset**, 1024→1280. Two consequences. (a) `thumbwidth` **echoes the request**: a 640
  request reports `thumbwidth: 640` while the bytes are 960×1443 (T388792). The only trustworthy
  signals are the `/Npx-` segment of `thumburl` and the decoded bytes — never label from the request
  *or* from `thumbwidth`. (b) Requests inside one bucket return the **same URL**, so
  `THUMB_WIDTH=640` pays the 960 price: 510,421 B for the sample file vs 142,727 B for the 500 bucket
  — **72 % fewer bytes for 27 % of the pixels**. The app already decodes the truth into `sent_px`;
  `about_payload()["request"]["thumb_width"]` and `/api/config`'s `thumb_width_requested` are
  request-side by design. Fix options: §12.
- **The model server normalises width to 640 px**, whatever you send — and never upscales (a 300×197
  original is sent as-is: 793 tokens). Evidence, free from the cache: `960×640 → 983`
  `input_tokens` while `960×1440 → 1,323`, i.e. **2.25× the sent pixels for 1.35× the tokens** — the
  count tracks the 640-wide geometry, not the bytes on the wire. So the requested width buys *no*
  tokens: the 960 rendition we download is discarded by the encoder, and requesting 1280 costs 80 %
  more bytes (916,726 vs 510,421) for an identical call. Token counts are deterministic per aspect
  ratio for the **six-question** schema — exact, read off the cache: 983 (3:2), 1,023 (4:3), 1,123
  (1:1), 1,323 (2:3); 16:9 would be 943 by the same arithmetic, but no 16:9 photo is cached, so that
  one is inferred. The `865/905/1,045/1,245` table this file used to carry is the **five-question**
  schema — DEVELOPER-NOTE-v0.4.1 §2 measured the added question at **+78 tokens** of instructions —
  so the live count is *old table + 78*, which holds exactly on all three ratios the cache can check.
  Diffing the two therefore looks like a 78-token model regression when nothing has changed: it is
  the sixth question. `usage.output_tokens` is always 0; this model writes no text.
- **`#` in a title silently truncates** (`File:X#1.jpg` → `File:X`). The parser truncates and warns.
- **`Datei:`/`Fichier:`/`Archivo:` are not Commons aliases**; they belong to de/fr/es wikis.
  `upload.wikimedia.org/wikipedia/<project>/…` names the wiki in the path — resolve on that wiki.
- **`Special:FilePath` answers 301 *or* 302** (301 when the name needs normalising).
- **Timing fields are not retroactive.** `ttfb_s` exists only for calls made after 0.2.0; cached
  answers from before that legitimately lack it, and the contract test treats a fully cached run as
  "not applicable" rather than failing. **Never fabricate timings for old cache entries.**
- **The 0.5 threshold is arbitrary.** Nothing scored above ~0.71 in any sample (24-photo batch:
  mean 0.361, max 0.707, 5 ≥ 0.5). Rank, don't threshold.
- **`used_last_hour` is in-memory, and it is the whole deployment's number.** `Budget` and every job
  live in the process, so a restart reports `0/100` while the endpoint's own quota for this client is
  untouched — and on Toolforge the pod restarts for reasons you do not control (rollout, eviction,
  node maintenance), not just `restart_app.py`. Because **every** model call is made by this server
  (§6), the endpoint sees one client for all users, so this counter is the entire tool's usage rather
  than one visitor's — which makes the reset more consequential, not less. Two things follow: (a) never
  read the budget line as "the hour is unspent" after a deploy, and never fire a 200-photo batch on
  that assumption; (b) the `100` is a **self-imposed** guard, not the endpoint's limit — WMCS traffic
  is in LiftWing's *known network* tier — effectively unlimited (§13) — so the
  real ceiling is not 100 and the binding protection is the 429 → stop path (§3.7), which
  does not depend on this counter being right. The UI labels it "… since HH:MM" for exactly this
  reason (`Budget.started`, surfaced as `counting_since`).
  **`HOURLY_BUDGET` is not enforced** (verified 2026-10-14 by reading `wiclient.score_image()` and
  `Budget` end to end): the only gate before a call is `budget.wait_seconds()`, the 429 cooldown —
  nothing compares `used()` with `limit`, and `used()` is read only by `status()` for display. The
  counter can therefore sail past its own ceiling and the UI will read `budget: 137/100`. Either
  enforce it or stop calling it a limit; until then the honest description is "counted and
  displayed", and the real brake on overuse is the 429 stop plus a human clicking the button. That
  distinction is why a URL that starts a run by itself is a bad idea —
  `MEMO-url-parameters-2026-10-14.md`.
- **A cached run measures nothing.** If every row says `from cache`, the elapsed time is the disk's,
  not the model's. Tick **run fresh** (`no_cache: true` on `/api/run` and `/api/eval`) — it bypasses the
  read side of the cache and re-scores every photo at one call each, with the hourly budget and
  `SPACING` still enforced. Bypassed answers are written back, so the calls are not wasted.
- **Positioning a thumbnail mixes two coordinate systems, and the charts got it wrong for a day.**
  A band's position is naturally measured *down* from the top (that is how the pose labels are
  placed with CSS `top`), while CSS positions a thumbnail *up* from the bottom (`bottom`). Using the
  same number for both flips the whole axis: every head-and-shoulders photo was drawn inside the
  **candid** band (`bottom: g.top + …` instead of `bottom: H - (g.top + g.height) + …`). The counts
  and the labels were right, so the earlier assertions — `5 strata`, `gridlines only in pose mode`,
  `thumbs present` — all passed. **Assert containment, not counts:** `test_render_dom.js` now
  derives each band from its label offsets and checks that every thumb's bottom edge falls inside
  its own pose's band (verified against a positive control: restoring the bug makes it name the
  mirrored bands). Anything that maps a data category onto a screen position needs that check.
- **A slow call is not a new image dimension, and cropping to a "known" one buys nothing.**
  Measured 2026-10-14 on a real 50-file AAAS set (34 distinct shapes — 26 of them appearing once):
  **33 of the 34 first sightings of a shape took 0.26–0.35 s**, and the shape-repeated group and the
  first-sighting group had the *same* median (0.31 s). The earlier "~6 s cold-start dimension load"
  in the `INFLIGHT` comment was an unmeasured guess from the v0.5.0 concurrency work — it had no
  support, and it is now removed rather than left to mislead.
  What the spikes actually are: **rare, isolated, ~4.6–6.8 s, ~1–2 % of calls.** Across ~166 calls
  the same file gave 6.757 s once and 0.53–0.74 s on ten other calls; another gave 4.60 s on an
  *identical repeat* of a call that had just taken 0.52 s, followed by twelve calls at ~0.45 s;
  a second 50-file run had **no** call above 0.75 s. So it is not the shape, not reproducible per
  image, and not a multi-call state (in the run that had one, its neighbours were 0.327 s and
  0.317 s). Mechanism **not established** — a second/cold backend replica or a gateway-side stall
  are the obvious candidates, and neither is observable from here.
  The only *measurable* cost driver is payload size: a 320 KB thumbnail averaged ~0.65 s against
  ~0.45 s for 145–183 KB ones (same shapes, ten calls each). Note what this rules out: cropping a
  photo to a familiar dimension does not make the service faster — and it would make the cache
  **wrong**, because the key is `(wiki, pageid, sha1, schema, served_width)` with no crop field, so
  a cropped and an uncropped run of one file would share a key while holding different inputs.
- **`quality` is defined only by its five legend labels** (0 unusable … 4 excellent) and by the
  640 px image the model actually sees. Do not describe it as a sharpness or lighting measurement.
- **A disabled button fires no click event, so a deep link must call the function, not the control.**
  `?run=1` did nothing at all until this was fixed (2026-10-14): the URL handler called
  `$("run").click()` while `setStage("idle")` had the button disabled, and the click was swallowed.
  The handler body is now `startRun()`, which both the button and the deep link call — and any future
  "programmatically press this control" shortcut has to check the control's state first.
- **The advertised Python floor was a lie until 2026-10-14.** README said "Python 3.9+" while
  `pdfmin.py` used `-> str | None` (PEP 604). That is evaluated when the *class is defined*, so on 3.9
  importing `pdfmin` raised `TypeError: unsupported operand type(s) for |` and took out every test
  that touched it. CI on 3.9 caught it the first time it ran; `check_compat.py` is the local lint that
  now catches it in milliseconds (annotation unions, `match`, `except*`). **Note what the lint does
  not flag**: `a | b` as an expression, because dict/set union is 3.9-safe — an earlier hand-rolled
  grep for PEP 604 found *none* of the three real sites while a naive AST scan over-reported six
  false positives, so trust `check_compat.py`, which discriminates on annotation context.
- **`check_docs.py` used to hardcode the owner's home directory** for the one upstream path it
  verifies (`scripts/parse-file-refs.py`, which lives in the Wikipedia-AI-Skills repo). It therefore
  passed on this machine and failed in CI — a repo check must not depend on whose laptop it runs on.
  It now takes `SKILLS_DIR` and reports that reference as *not verified here* when the clone is
  absent, instead of failing.

## 5. The endpoint can be ~50× slower than its baseline — and that is not your bug

Measured: warm calls (62 recorded, 2026-10-02 and 2026-10-12) had a **median of 0.54 s** and a worst
case of 6.95 s. On **2026-10-13, 12:16–12:45 UTC**, 20 calls had a **median of 28.63 s** (range
27.43–29.40), with no 429s; a text-only call took 27.8/29.0 s and the same question with an image
28.7/28.6 s — so it is not the image, the download, the aspect ratio or this app. For context, the
Wikitech page's only published benchmark is for a **different, larger model on a different endpoint**
— `llm-qwen36-27b` (FP8), *internal* endpoint, single replica, 2026-07-17 — and reports 197 ms to first
token, 3.6 s end-to-end p50 at concurrency 1, and 18 s end-to-end p50 at concurrency 64. The page
states the platform is experimental with **no availability SLA**, and that public-endpoint and
per-model baselines "will follow". So there is no published baseline for `llm-clef-flash` itself: the
0.54 s `BASELINE_WARM_S` in this repo is our own measurement, not a vendor figure.

**This is not settled infrastructure — it is a brand-new service with its own ticket.**
`llm-clef-flash` was deployed under Phabricator **T440223** (`Open, Needs Triage`, §13), where the
stated target is **under 1 second per image**. On **2026-10-14 12:39 UTC** it met that: 0.36/0.22 s
text-only, 0.45/0.42 s with an image, all HTTP 200 (`probe_latency_now.py`). So the 28-57 s episodes
recorded here are the *service* missing its own target, not this app misbehaving — and equally, a run
that is fast today is not evidence that this app got faster. **Read §13 before treating any latency
number in this file as a property of the tool.**

How the app handles it: every call records `wall_s` (total) and `ttfb_s` (time to first byte — the
gateway holding the request) plus `x-envoy-upstream-service-time`, and `latency_summary()` labels the
run `normal` / `elevated` / `service-side` against `BASELINE_WARM_S` (0.54 s, env-overridable). The
verdict shows in the UI, the run log and the reports.

**A 5xx is retried once; a 4xx never.** The gateway's `503 upstream connect error or disconnect/
reset before headers … connection timeout` means the model was never reached, so the photo was not
processed and one retry (2 s backoff, logged, one attempt only) recovers most of them — the app
otherwise loses the photo outright, which is what a real 503 did on 2026-10-14. `429` keeps its own
single retry driven by the server's `Retry-After`, and a `4xx` (malformed body, bad User-Agent) is a
client-side fault that retrying cannot fix. `UPSTREAM_RETRY_CODES` / `UPSTREAM_RETRY_BACKOFF` in
`wiclient.py`; `test_pipeline.py` asserts one retry, no loop, and no retry on a 400.

**Before "fixing" a slow run: run `probe_latency_now.py` (4 calls) and check whether text-only is
also slow.** If it is, the app is innocent — record the number and move on. Do not add retries or
concurrency. On the **dev host** that would burn a shared 100 req/h anonymous budget; on **Toolforge**
the quota is lifted (§13), so the reason changes rather than disappears — the service is new (T440223)
and a public tool should not be the thing that load-tests it.

## 7. Next steps, ranked (with the trap that makes each worth doing)

**Small, high value**
1. **Settle the concurrency question, then maybe re-enable 2 streams** — the owner suspects the
   endpoint punishes two concurrent calls, so `INFLIGHT` defaults to 1 (serial). The overlap
   machinery is built and unit-verified (2 streams, 35.5 s vs 61.4 s serial when the endpoint was
   at ~30 s/call). One production run of 2 fresh photos with `INFLIGHT=2` — comparing per-call
   `wall_s` against serial — settles whether the endpoint queues same-origin calls. Keep serial
   unless the measurement is clearly neutral or better.
2. **Periodic latency probe + trend** — the endpoint moved 50× in a day with no announcement; a cron
   that runs `probe_latency_now.py` hourly and records the median makes the app's verdict meaningful
   and gives a real regression record (see the observability reference in §9). Keep the **date** on
   every number, and read §13 first: this app is probably the heaviest consumer of a brand-new
   service (**T440223**), so a slow hour is evidence about the *service* — worth handing to the ML
   team on that ticket — rather than something to fix here.
2b. **Identify the ~1–2 % slow calls.** §4 measured them (4.6–6.8 s, isolated, not shape- or
   image-keyed, ~166 calls observed) and refuted the "new dimension" explanation, but the mechanism is
   still unknown — a second/cold backend replica and a gateway stall are the candidates and neither is
   observable from here. Worth one measurement before anyone optimises the image size again.
3. **Show the full distribution per photo on demand** — the API already returns the whole probability
   vector; exposing it costs nothing and helps users trust (or distrust) a score.
4. **Cache persistence on Toolforge** — the deployment runs `--mount=none`, so `cache/` is wiped on
   every webservice restart (re-scoring then costs one call per photo again). Options: deploy with
   the NFS mount and point `CACHE_DIR` at the tool home, or accept the wipe (WMCS origin is fast
   when the endpoint is warm). Decide before the photo count grows.
5. **Decide how the headline is presented** — research is done and the decision is pending (see §11).
   The evidence does *not* support swapping the question: today's `infobox_ready` separates candidates
   better than any rewrite tested. The cheap fix is presentational (rank + percentile within the run);
   any question change needs a 12+ portrait run and hand labels first.

**Medium**
6. **`Category:` / PetScan / SPARQL / PagePile input** with an explicit member cap and a confirmation
   step ("Category:Foo has 1,240 files; score the first 200?"). The parser already warns instead of
   guessing; this needs the UX, not the API work. **PagePile first** (PRD F17): it is one fixed-host
   call with a numeric id (`pagepile.toolforge.org/api.php?action=get_data&id=<id>`), which is why it

   Reuse the `?list=` pattern: prefill the box and let a human press *Validate files*.
7. **Run history + run-to-run diff** (small SQLite or JSON store): "these 12 photos got worse after
   the file was overwritten / after I changed the schema".
8. **Server-sent events instead of 1 s polling** — nicer clocks, less chatter; the incremental
   renderer is already the right shape for it.
9. **Thumbnail proxy + local cache** — makes the deployment fully server-origin (and offline-capable),
   at the cost of the app's bandwidth.

**Larger / research**
10. **Calibration study** — label ~100–200 photos by hand, produce a precision/recall curve, then

## 11. Question design: the "infobox ready" experiment (2026-10-13)

Full write-up, raw answers and chart: `research/wording-experiment-2026-10-13.md`,
`research/wording_experiment.jsonl`, `research/wording_comparison.png`.

**What was actually adopted (same day, after the pilot):**

1. **`publish_ready` added to the schema** — a two-option `choice` ("this photograph is the one to
   use" / "choose a different photograph instead"), i.e. variant V5 from the pilot. It is the model's
   own answer; the app shows P(publish). First live call after the change: **publish 0.937 / pass
   0.063** on a photo where the infobox wording gave 0.746 — the two-way question is decisive where
   the threshold question was not.
2. **A composite is now the ranking key**, defined in `wiclient.composite()`:
   `min(face_visible, eyes_to_camera) × pose weight` (head-and-shoulders 1.0, three-quarter 0.9, full
   body 0.6, candid 0.5, group 0.25). `infobox_ready` is still asked and still shown, but it no longer
   orders the list. The composite must always be labelled as our arithmetic (invariant 8).
3. **Candidate spread is reported per run** for all three headline numbers (composite, P(publish),
   P(infobox)) — candidates above the floor, range, median gap between neighbours, dead-zone share and
   the leading three titles. Never sd (invariant 9).
4. **Because adding a question changes the schema hash, every cached answer was invalidated** and each
   photo needs one fresh call. That is by design, not a bug: answers to one question are only
   comparable within an identical question set.

**Still open from the pilot:** the wider validation (12+ portraits, composite vs P(publish) vs
P(infobox), then hand labels). The pilot could not settle whether the composite ranks the *middle* pair
correctly — it and P(publish) both put Jenni above Irina while every other wording did the opposite.

The complaint that started it: `infobox_ready` sits in 0.5–0.6 for almost everything, and its wording
("lead image (infobox portrait) of a Wikipedia biography") needs a lot of unpacking.

**The free half of the answer** (`analyze_question_spread.py`, 57 cached photos, no API calls): the
split is not by question *type* — the 0–4 `quality` score is the most compressed question we ask
(sd 0.145, 60% in 0.35–0.65) — it is by *criterion kind*. Questions about something **visible in the
frame** spread across nearly the full range (`face_visible` sd 0.372, `eyes_to_camera` sd 0.350,
2–7 of 57 in the band); questions that ask for an **editorial or aesthetic** judgement collapse
(`infobox_ready` sd 0.229 with 47% in the band; `quality` 60%).

**The live half** (`tune_infobox_question.py`, 4 photos × 5 wordings, 20 calls, all HTTP 200,
median 57 s/call) tested the rewrites. P(publish-ready):

| photo (today's value) | today | plain+criteria | professional portrait | score 0–4 | choice publish/pass | composite |
|---|---|---|---|---|---|---|
| Andrey (0.740) | 0.676 | 0.920 | 0.960 | 0.676 | 0.877 | 0.763 |
| Irina (0.528) | 0.357 | 0.834 | 0.944 | 0.642 | 0.708 | 0.398 |
| Jenni (0.208) | 0.190 | 0.814 | 0.939 | 0.594 | 0.846 | 0.544 |
| logo (0.010, control) | 0.024 | 0.052 | 0.164 | 0.071 | 0.037 | 0.003 |
| sd | 0.241 | 0.350 | 0.339 | 0.247 | 0.341 | 0.277 |
| in 0.35–0.65 | 1/4 | 0/4 | 0/4 | 2/4 | 0/4 | 2/4 |
| **range among the 3 portraits** | **0.486** | 0.106 | **0.021** | 0.082 | 0.169 | **0.365** |

**The finding that matters:** every rewording emptied the dead zone and improved global sd — and every
one of them separated the three real portraits *worse* than the wording users complained about. The
"professional portrait" wording leaves them at 0.939 / 0.944 / 0.960: range 0.021, three photographs
effectively tied. Rewording moves the pile-up from the middle to the ceiling.

**Recommendation (awaiting the owner's decision):**
1. Don't adopt the "plain + criteria", "professional portrait" or 0–4 score variants. Each emptied the
   dead zone and each separated the real portraits *worse* than the wording users complained about.
2. **Don't change the headline question yet.** On this sample the current wording separates the three
   candidates best (range 0.486 vs 0.365 for the composite, 0.169 for the `choice` variant, 0.021 for
   the "professional portrait" wording). "The numbers all look like 0.5" is a resemblance complaint,
   not an ordering complaint — and ordering is what triage consumes.
3. **Fix the presentation instead** (no schema change, no calls): show a rank and percentile within
   the run next to the probability ("3rd of 24 · top 13%").
4. If a switch is still wanted, the candidates to validate are the composite
   `min(face_visible, eyes_to_camera) × pose weight` (head-and-shoulders 1.0, three-quarter 0.9,
   full body 0.6, candid 0.5, group 0.25; widest corpus-level spread, sd 0.352 vs 0.229) or the

   answers*, not a model probability.
5. Report **candidate spread** alongside the run and stop using sd as a proxy for question quality.
6. Validate before shipping: 12+ portraits (today's wording vs the `choice` variant; the composite is

**Reopen / redo if:** the wider run reverses the portrait order, hand labels show the composite ranks
worse than today's question, or the platform swaps the model.

## 12. Thumbnail width: the 640 → 960 bucket (measured 2026-10-13)

Settled with `probe_thumb_ladder.py` — 10 requests against one 4024×6048 original, all raw responses
cached in `cache/ladder/`, so every re-run is free:

| `iiurlwidth` asked | `imageinfo.thumbwidth` | `/Npx-` in `thumburl` | bytes downloaded |
|---|---|---|---|
| 120 | 120 | 120 | 10,377 |
| 250 | 250 | 250 | 36,673 |
| 320 | 320 | **330** | 62,804 |
| 500 | 500 | 500 | 142,727 |
| 600 | 600 | **960** | 510,421 |
| 640 | 640 | **960** | 510,421 *(same asset as 600)* |
| 800 | 800 | **960** | 510,421 *(same asset)* |
| 960 | 960 | 960 | 510,421 |
| 1024 | 1024 | **1280** | 916,726 |
| 1280 | 1280 | 1280 | 916,726 *(same asset as 1024)* |

**What this means.** The app asks for 640, which is one notch below the 960 step, so it downloads the
960 asset — and the model server then discards 73 % of those pixels, because it normalises width to
640 before its encoder (§4). Nothing is *wrong*: `sent_px` decodes the truth and the reports label
from it. But the request and `thumbwidth` both say 640 while the bytes are 960, and the app pays 3.6×
the bytes of the nearest bucket below (142,727).

### Options, cheapest first

**A. Make the request honest — `THUMB_WIDTH=960`.** Measured: 640, 800 and 960 return the
**identical `thumburl`**. So this changes nothing about the bytes, the tokens or the scores; the only
effect is that the cache key's last field moves `640 → 960`. Because the bytes are the *same file*,
existing entries can be **renamed rather than re-scored** — verify byte-identity first
(`sha1sum cache/thumbs/*`) instead of assuming it. Buys: the label matches the asset and §4's trap
stops being true. **Do this one first — it is free.**

**B. Stop trusting `thumbwidth`; record the served width.** Parse `/Npx-` out of `thumburl`,
cross-check it against `image_size()` of the downloaded bytes, keep `served_w` *beside* `requested_w`,
and expose `served_w` in `/api/config` and the About payload. A few lines. Buys: the mislabelling
class of bug cannot recur, and it generalises to SVG/PDF/video renders, where the served width has
nothing to do with the request. Note the cross-check is the point — `thumbwidth` echoing the request is
a documented Wikimedia behaviour (T388792), not a relay or proxy artefact.

**C. Halve the bytes — request the step at or below the target (500).** This is the sanctioned
upstream pattern. 142,727 B vs 510,421 B is **72 % less downlink for 27 % of the pixels**. **But it is
not free.** The model would normalise a 500-wide image, i.e. *upsample* it, so the pixels the encoder
sees are worse than today's 960→640 downscale, and the width in the cache key invalidates every stored
answer. This needs the treatment the wording experiment got (§11): score the same N photos both ways
and compare **ordering**, not values. Do not ship it on the byte saving alone.

**D. Cap the long edge instead of the width.** A 2:3 portrait at 960 downloads 1.5× the pixels of a
16:9 at the same width, so choosing the bucket per aspect ratio would even the bytes out — and it
would destroy the one thing §4 relies on, "token counts are deterministic per aspect ratio".
**Not recommended** unless bytes become a real constraint.

**E. Decouple the report image from the sent image.** `thumb_bytes()` embeds *exactly* the bytes that
were sent, so option C would also shrink the thumbnails inside the PDF and the Markdown report. If C is
ever taken, decide explicitly whether the report should re-fetch a larger rendition (one extra
download per photo) or accept the smaller image.

**Do now:** A + B. Leave C alone until someone actually needs the bandwidth — 100 photos/hour × 218 KB
is ~22 MB/h, and the endpoint charges in **tokens**, which the requested width does not change.

### Done 2026-10-14: A + B implemented

**A** — `wiclient.THUMB_WIDTH` defaults to **960**, a real `THUMB_LADDER` step, alongside the new
`THUMB_LADDER` and `MODEL_MAX_WIDTH` constants. `test_thumb_width.py` asserts that the configured
width *is* a ladder step and that 640 is not, so the 640-in-a-960-bucket mistake cannot come back
silently.

**B** — `wiclient.served_width_from_url()` reads the `/Npx-` segment (handles `/page1-960px-` and
video keyframes); `resolve()` puts `requested_w` and `served_w` on every item; `_download()`
cross-checks `served_w` against the decoded bytes and sets `width_mismatch` on the item (logged and
listed in the run log) if a CDN or proxy ever serves a rendition other than the one the URL
advertises. `served_w` and `sent_px` reach the UI, the JSON and the CSV; the About panel and
`/api/config` name the ladder and `MODEL_MAX_WIDTH` instead of implying the request was honoured.

The cache key now uses the **served** width (§3.4), which is what makes A free rather than merely
correct: because 640 and 960 alias to one asset, the existing `*-640.json` entries keep working
under the new key. Verified — all 11 local entries were renamed `*-640.json` → `*-960.json`, and a
live 2-photo run came back `from_cache: true` in **0.15 s with no model calls**, `served_w: 960`,
`sent_px: 960x720` / `960x1440`, `width_mismatch: null`. `test_ui_contract.py` passes on the new
build (app boots as `thumb 960px`); the full offline suite is green.

**Canary:** if a served width ever looks wrong, run `python3 probe_thumb_ladder.py [File:Title]` before
touching the app. A Wikimedia-side ladder change is exactly the kind of event that would otherwise
silently alter the images the model sees — and with `thumbwidth` echoing the request, the app would
not notice.

## 13. Upstream service context — `T440223` (the endpoint is new, and it moves)

**The ticket:** **[T440223 — "Deploy an open-weight decision model for classification use cases"](https://phabricator.wikimedia.org/T440223)**
· status **`Open, Needs Triage`** · Public.

It is the deployment request to the ML team for *exactly* the service this app calls: a
**decision-model** (not a chat model) on LiftWing, choosing between Cloudflare's **Clef** and a
Cygnet-type setup. Its description is the authoritative statement of the semantics this app depends
on — an input plus typed questions (yes/no, choice from a list, score on a rubric) **returning a
probability per option in a single forward pass, generating no text**. That is precisely the
`noul` / `choice` / `score` vocabulary quoted from the model card in §4 and the About panel.

**Why it belongs in this file.** Three consequences follow, and every one of them has already been
misread at least once:

1. **The service is new and being actively adjusted.** A change on the serving side shows up here as a
   change in *this app's numbers* — latency first, but scores too if the model or its image handling
   is retuned. Any such change is upstream by construction.
2. **This app is probably the heaviest consumer of it.** A 200-photo WikiPortraits run is 200
   image-bearing calls through a service chosen for low-volume classification work. So this app is
   as much a load test of the endpoint as a client of it, and an unusual result here is at least as
   likely to be evidence *for* the ML team as a bug against this code.
3. **The ticket states the target: under 1 second per image.** That is the yardstick for judging a
   slow run — not our own variance, and not the published Wikitech benchmark, which is a different
   and larger model.

The WikiPortraits work and this ticket are the same thread: the evaluation was first reported *on*
the ticket (comment 2026-10-05, attaching `clef-flash-wikiportraits-live-run-cloudflare-small.pdf`),
noting that pose, quality, eyes and face visibility worked while "fitness for infobox needs some
tweaking" — which is why §11's composite exists and why the headline question is unchanged.

**The latency record is really a record of the endpoint, not of this app:**

| when (UTC) | per-call | context |
|---|---|---|
| 2026-10-02, 2026-10-12 | **0.54 s median** (worst 6.95 s) | 62 calls — the `BASELINE_WARM_S` value |
| 2026-10-13 12:16–12:45 | **28.63 s median** (27.43–29.40, n=20) | no 429s; text-only 27.8/29.0 s, image 28.7/28.6 s |
| 2026-10-13, later | **~57 s** | the wording experiment (§11) ran entirely at this speed |
| 2026-10-14 12:39 | **0.42 s median** | 4 calls, all HTTP 200 (text 0.36/0.22 s, image 0.45/0.42 s) |

Two orders of magnitude, twice, in 48 hours. **Always date a latency number** — an undated "the
endpoint is slow/fast" in this repo is unfalsifiable, and a stale one has already caused a wrong
conclusion (§4, the dead-thread `NameError` misreported as "the endpoint degraded to >25 min/call").

**The failure mode, for recognition:** the ticket carries the server-side trace — `EngineDeadError` →
`EngineCore encountered an issue` raised in the serving container's model module
(/srv/app/model.py — that path is inside the LiftWing container, not this repo) → `vllm.v1.engine` →
**HTTP 500** on `POST /v1/models/llm-clef-flash:predict`. That is the same `EngineCore` outage recorded
in §6 for 2026-10-13. So when a run dies at the pre-flight (§3.7), or 500s rather than 429s appear,
the app is correct to stop and say so — and the evidence belongs on this ticket.

**What limits us: the `LiftWingLLM` policy** ([T426749](https://phabricator.wikimedia.org/T426749)). Every public `llm-*` endpoint
is governed by it in the REST Gateway, described upstream as "a coarse, interim limit until
cost/token-based limiting lands". As of **2026-10-14** the table is — verbatim copy in
`research/wikitech-liftwing-limits-2026-10-14.txt`:

| client class | limit | who |
|---|---|---|
| public / anonymous | **100 / hour** | anonymous, user-agent-only **and authenticated** users — a shared *per-client* budget across **all** `llm-*` models |
| **known network** | **effectively unlimited** | **WMCS — Cloud VPS and Toolforge** (CDN `x-trusted-request: A`) |
| known client | effectively unlimited | networks associated with a known client (`x-trusted-request: B`) |
| approved bot | effectively unlimited | community-approved bots (JWT auth) |

The same code therefore runs in **two different regimes**, and nearly every number in this file was
measured in the second one:

- **Deployed on Toolforge** (production) → *known network*, effectively unlimited. No external quota
  enforces `HOURLY_BUDGET`, and neither `SPACING` nor `INFLIGHT=1` is required by one either. The page
  calls this the recommended way to get the higher limit: no API key, no configuration, it follows
  purely from where the code egresses.
- **On a laptop / the development host** → *public / anonymous* → **100 calls/hour**, shared per client
  across all `llm-*` models — not per model, not per user. That is why §5's experiments and the
  `BASELINE_WARM_S` figure are conservative.

Three consequences:

1. **The `200,000 req/h` figure this file used to quote was wrong** and is removed. The page says
   "effectively unlimited" and names no number: do not cite a figure the source does not state.
2. **Token-based limiting is announced as the successor** to this interim policy. This app sends
   ~1,000-1,300 input tokens per photo and generates none (`output_tokens` is always 0), so a token
   budget would constrain it differently from a call budget — re-read this section before assuming a
   200-photo run is cheap.
3. **The self-imposed cap stays anyway.** "Unlimited" is not a licence to hammer a service that is
   still new (T440223), and a public tool with no login must not become a load harness aimed at the
   endpoint. Same shape of answer as §5: measure first, and don't.

**Confirmation of the single-client model:** the page notes that LiftWing Studio "runs on Cloud VPS (a
known network)" and that "the gateway sees Studio as a single WMCS client rather than individual
users". That is precisely this app's situation — one server origin for every visitor. It is both why
Toolforge gets the unlimited tier and why the in-app counter (§4) is the only per-user pacing that
exists.

**What to do with this, in order:**

1. Re-measure before concluding: `python3 probe_latency_now.py` (4 calls). **If text-only is also
   slow, the app is innocent** — record the dated number and move on.
2. Do **not** compensate by adding retries, raising `INFLIGHT`, or shortening `SPACING`. On the dev
   host that burns a genuinely shared 100 req/h budget (§3.7); on Toolforge the quota is lifted (§13),
   so the reason is courtesy rather than a cap — and neither is a reason to push harder on a service
   that is already struggling.
3. Hand the measurement to the ML team on **T440223** (dated, with text-only vs image split, and the
   HTTP status). **Hand it over, do not post it** — this agent's default for Phabricator is
   read-only, and a Wikimedia account holder should file or comment in their own name.
4. Only then consider whether §7's probe-and-trend cron is worth building, since that is what makes
   step 3 cheap and routine.

**What this app logs — audited 2026-10-14; keep it this way.** Two layers, and only one is ours:

| layer | contains | notes |
|---|---|---|
| **Toolforge's own request log** (`/data/project/<tool>/logs/`, plus the ingress) | client **IP** and **User-Agent** | not ours to change; per the `wikimedia-security-and-privacy` skill, do **not** publish it, copy it into the repo, or ship it to any third party (Sentry/Logstash/…) |
| **the app's stdout** (container log) | `[time] "METHOD path HTTP/1.1" status -` | no IP, no User-Agent by construction (`log_request` formats only the request line), and since 2026-10-14 **no query string** (`app.redact_query()`), because a `?list=` link carries up to 4 KB of user-supplied file names |
| **the per-run log** (in memory; the UI's *Run log*) | resolution counts, per-photo scores, cache hits, retries, and the **full** gateway error body on failure | dies with the pod, so it is not a durable record; the item *row* caps its message at 160 characters |
| **`cache/*.json`** | per photo: `title`, answers, `http`, `wall_s`, `ttfb_s`, token counts | a record of *which files were scored*, not of who scored them; wiped on restart (`--mount=none`) |

So the model and the pipeline are measurable; **visitors are not identified**. No IP, no User-Agent,
no cookie, no session, no third-party analytics, and nothing is derived about the people *in* the
photographs (§8).

**If usage measurement is wanted, add counters, not richer logs** — one structured line per
completed run: photos scored, cache hits, fresh calls, 429s, upstream retries, median call time, run
wall time, and the *item count*. Never the titles, never the query, never a client attribute; that
answers "is it used, is it fast, is it failing" with nothing personal in it. Retention is bounded
either way: the container log rotates on the platform, and a counters file inside the pod spans one
pod lifetime at most (`--mount=none`), so a real trend needs the NFS mount (§7.4) or the platform's
own log retention.

**One caution.** Because this app is a heavy consumer of a young service, "the app is fine" is not
the same as "the numbers are stable". Latency is the *visible* churn; if the serving stack's image
preprocessing or the model build changes, the probabilities can move without any error being
returned — which would invalidate comparisons against cached answers. §4's schema hash covers *our*
prompt changes, not *their* model changes. If a rerun of a cached photo ever disagrees with its
stored answer, suspect the service first and re-check this ticket.
